# RAG 接入后的 WebServer 性能与上传图片回归修复

## 1. 用户看到的问题

- 原有页面响应变慢。
- 图片上传后社区记录存在，但浏览器显示破图。
- 加载社区页面时多个连接长期积压。

## 2. 图片实际没有上传失败

日志证明上传链路全部成功：

```text
upload file saved, size=119594
upload db saved
upload community page rebuilt
upload success
```

对应文件是有效的 1920×1080 PNG。因此故障发生在后续静态文件响应阶段。

## 3. 破图的根因

旧路由通过 URL 最后一个 `/` 后面的第一个字符识别特殊页面：

```cpp
*(p + 1) == '1'
*(p + 1) == '5'
*(p + 1) == '6'
*(p + 1) == '7'
```

上传文件使用随机哈希前缀，例如：

```text
/uploads/1e7d4c302b9f7465_example.png
```

这个文件因为 basename 以 `1` 开头，被错误映射成登录页面。浏览器得到的是
`text/html`，却尝试把它显示为 PNG，所以出现破图。随机前缀以 5、6、7 开头时也有
同样问题，因此故障看起来是“偶发”的。

修复后只精确匹配：

```text
/0
/1
/5
/6
/7
/2CGISQL.cgi
/3CGISQL.cgi
```

普通文件名不再进入特殊 CGI/演示页面路由。

## 4. 静态图片访问策略

`/community.html`、上传页面和上传接口仍需要登录，但 `/uploads/*` 作为页面中的静态
媒体可以直接读取。这样 Session 到期时不会把登录 HTML 返回给 `<img>`。

这个选择适合当前公开社区演示。若以后上传内容需要私密访问，应改成带过期签名的媒体
URL或专门的鉴权下载接口，而不是返回登录 HTML。

## 5. 响应速度修复

### 监听队列

`listen()` backlog 从 5 提升到系统 `SOMAXCONN`。当前环境实际显示 4096，能够容纳
浏览器并行建立的图片连接。

### 写事件

删除每秒遍历所有待写连接的兜底重试。非阻塞响应继续通过 epoll 的 `EPOLLOUT`、部分
写和 `EAGAIN` 驱动，避免无意义的一秒级轮询延迟。

### 社区页面

社区页面继续查询并展示 MySQL 中的全部帖子，图片也继续直接显示，不限制为最新 10 条，
不改成只提供原图链接。服务器重启后第一次登录访问社区会自动重建页面，上传成功后也
会立即重建。

## 6. RAG 与旧业务隔离

流式 `/api/ask` 现在立即返回 SSE 连接，然后在独立的受限模型流线程中执行：

```text
Query Embedding -> TopK -> Prompt -> LLM stream
```

这些网络等待不再占用原 WebServer 的 8 个业务线程。模型流总并发上限仍为 16；此外
单 IP RAG 请求使用令牌桶限制，突发容量 4、每秒恢复 0.5 个，避免模型请求冲垮旧服务。

非流式 `/api/ask` 主要保留给命令行兼容测试，仍会同步等待模型；浏览器页面固定使用
流式模式。

## 7. 回归结果

- 随机前缀为 1、5、6、7 的四张历史图片全部返回 `image/png` 和完整 119594 字节。
- 公网访问历史上传图片返回 HTTP 200，约 2ms（服务器回环公网测试）。
- 20 个并发图片请求全部 HTTP 200，最慢约 19ms。
- backlog 已变为 4096。
- 未登录 RAG 请求立即返回 401，没有触发模型调用。
- 全部单元测试通过。
