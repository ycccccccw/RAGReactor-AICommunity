# 阶段 5：工程增强（简单说明）

## 1. 原项目已经有令牌桶吗？

有。阶段 5 没有删除或重复实现它，而是保留原来的分路径令牌桶：

- 登录：突发 10 次，平均每 6 秒恢复 1 个令牌。
- 注册：突发 5 次，平均每 12 秒恢复 1 个令牌。
- 上传：突发 5 次，平均每 10 秒恢复 1 个令牌。
- 社区页面：突发 20 次，每秒恢复 2 个令牌。
- 普通请求：突发 50 次，每秒恢复 5 个令牌。
- RAG `/api/ask`：突发 4 次，每秒恢复 0.5 个令牌。
- `/uploads/*` 图片不参与普通限流，避免一个页面的多张图片被误判为攻击。

令牌桶由互斥锁保护，多线程访问不会同时修改坏同一个桶。被 RAG 限流的请求返回 HTTP 429，
并增加 `rate_limited_total` 指标。

## 2. 语义缓存怎么工作？

第一次问题仍执行：

```text
问题 -> Embedding -> TopK -> LLM -> 保存答案
```

以后问题先生成 query embedding，再与历史问题向量计算余弦相似度。默认相似度达到 0.95
就直接返回缓存答案，不再调用 LLM。缓存默认最多 100 条、10 分钟过期，容量满后淘汰最早
使用的内容。非流式响应包含 `cache_hit`，SSE 的 `sources` 和 `done` 事件也包含它。

## 3. 超时、熔断和降级

- 连接模型服务默认最多等待 3 秒。
- Embedding 整体默认最多等待 10 秒。
- LLM 整体默认最多等待 30 秒。
- 连续 3 次上游失败后打开熔断器 30 秒。
- 熔断期间不再请求百炼，立即返回 `RAG_CIRCUIT_OPEN`。
- 流式请求在 LLM 失败前已经返回检索来源，因此页面仍能展示 sources，然后收到明确的
  `error -> done`，这是当前版本的服务降级策略。

所有参数都可以在 `.env` 中调整，示例见 `.env.example`。

## 4. Request ID 和日志

每个 API 请求会得到类似 `req-12` 的 request ID：

- JSON 成功和错误响应中返回 request ID。
- SSE 的 sources/error 事件中返回 request ID。
- HTTP 响应头返回 `X-Request-ID`。
- 服务日志写入 JSON 风格的 `api_response` 记录，包含 request ID、路径和状态码。

## 5. 监控指标

健康检查：

```bash
curl http://127.0.0.1:9006/api/health
```

新增字段包括 `semantic_cache_entries` 和 `circuit_open`。

登录后可以访问：

```text
GET /api/metrics
```

返回 API 请求数、问答数、缓存命中/未命中、限流次数、上游失败、熔断拒绝和当前流式并发。
该接口需要有效 Session，避免把运行数据直接暴露给未登录用户。

## 6. 验收重点

1. 连续询问相同或高度相似的问题，第二次响应应出现 `cache_hit: true`。
2. 短时间连续请求 `/api/ask` 超过突发容量，后续请求应返回 HTTP 429。
3. 把模型地址临时改成不可访问地址并重启，连续失败达到阈值后应快速返回
   `RAG_CIRCUIT_OPEN`。
4. 查看 `/api/health` 和登录后的 `/api/metrics`，确认缓存、失败和限流计数发生变化。
