# RAG 问答与 AI 社区推荐融合实施计划

## 1. 目标

将当前的 RAG 问答和社区展示融合为一个“智能知识社区”，共用内容理解、Embedding、
向量索引、混合检索、重排、容错和监控能力，并提供两个产品出口：

- **AI 问答**：检索知识文档和可选的高质量社区内容，由大模型生成带来源的回答。
- **为你推荐**：根据用户兴趣检索和排序社区帖子，直接展示原内容，不调用大模型生成答案。

最终形成以下流程：

```text
知识文档 ─┐
          ├─> 统一内容处理 ─> Embedding/索引 ─> 混合检索/重排
社区帖子 ─┘                                      │
                         ┌───────────────────────┴──────────────────┐
                         │                                          │
                  RAG 问答与引用                             个性化社区 Feed
                  显式问题作为查询                           用户兴趣作为查询
```

这不是重新开发两个项目，而是在现有 RAG 检索内核上增加内容类型过滤、社区索引和推荐出口。

## 2. 当前项目基础

项目当前已经具备：

- C++17 Web 服务、登录会话、MySQL 连接池和文件上传。
- 社区帖子表 `user_posts`，以及图片、视频和文本发布能力。
- Embedding Provider、百炼 Embedding 接口和向量存储。
- HNSW 近邻检索、BM25、混合召回和 Rerank。
- `/api/ask` RAG 问答、SSE 流式响应、超时、重试、熔断和指标。

目前社区页面由服务端读取全部帖子后重建静态 `root/community.html`，仅按帖子 ID 倒序展示，
没有分页、行为采集、用户画像和个性化排序。因此本次修改的第一步是把社区展示改成动态 API。

## 3. 完成后实现的功能

### 3.1 统一 AI 内容层

- 知识文档与社区帖子使用统一的内容元数据结构。
- 每条索引内容具有 `source_type`、`source_id`、作者、发布时间和状态等字段。
- 知识文档与帖子可以共用 Embedding、向量存储、HNSW、BM25 和重排代码。
- 检索时可以按 `knowledge` 或 `community` 过滤，避免两类数据互相污染。
- 帖子发布后异步或延迟生成向量；AI 服务异常时不影响正常发帖。

### 3.2 个性化社区 Feed

- 动态分页加载，不再为每次发布重建完整 HTML 文件。
- 采集曝光、打开、停留、点赞、收藏、快速划走和不感兴趣行为。
- 根据近期行为和长期行为生成用户兴趣向量。
- 综合语义相似度、热度、新鲜度、负反馈和探索流量进行排序。
- 支持冷启动、看过降权、作者去重和 AI 故障时回退热门/最新内容。

### 3.3 RAG 与社区的产品融合

- RAG 回答下展示相关社区讨论。
- 社区帖子提供“向 AI 追问”和相关知识内容入口。
- 用户问答主题与社区行为共同影响兴趣画像。
- 可配置 RAG 是否检索高质量社区帖子；社区来源会单独标识，避免把用户经验当成权威资料。

### 3.4 可观测与安全

- 记录 Feed 延迟、召回数量、回退次数、Embedding 失败和行为写入失败等指标。
- 所有写接口验证登录状态和 CSRF Token。
- 对行为接口做频率限制、参数校验和幂等控制。
- 保留按时间排序的回退通道，推荐模块异常时社区仍可使用。

## 4. 预计工期

以当前代码为基础，由我连续实施并具备可用的数据库和百炼测试配置时，工程工作量预计为
**12～18 个工作日**。如果只完成可演示的最小版本，预计 **7～10 个工作日**。

| 范围 | 预计时间 | 结果 |
|---|---:|---|
| 最小可用版 | 7～10 天 | 动态 Feed、行为采集、规则排序、文本向量推荐、故障回退 |
| 完整融合版 | 12～18 天 | 统一内容层、兴趣画像、多路召回、RAG/社区双向入口、完整测试与指标 |
| 后续模型优化 | 依赖数据量 | 使用真实行为训练点击、停留或收藏预测模型 |

工期不包含大规模 UI 视觉设计、视频逐帧理解、内容审核平台、移动 App 和生产环境集群改造。
外部 API、数据库或部署环境不可用时，对应的联调时间需要顺延。

## 5. 分阶段修改计划

### 阶段 0：基线确认与设计冻结（0.5～1 天）

修改内容：

- 确认当前编译、测试、登录、发帖和 RAG 问答均可运行。
- 固化 Feed JSON、行为事件和统一内容元数据格式。
- 明确知识内容和社区内容的可信度边界。
- 准备可重复执行、非破坏性的数据库迁移脚本。

交付物：

- API 数据结构说明。
- 数据库迁移脚本。
- 修改前测试基线记录。

验收标准：现有 `make test` 通过，原有问答与发帖功能未被破坏。

### 阶段 1：动态社区 Feed 与行为采集（2～3 天）

修改内容：

- 新增 `GET /api/community/feed?cursor=...&limit=...`。
- 新增 `POST /api/community/action`。
- 社区页面通过 JavaScript 获取分页数据，并支持继续加载。
- 增加曝光、停留、点赞、收藏、跳过和不感兴趣事件表。
- 保留旧页面或时间流作为功能开关下的回退方式。

主要涉及：

- `api/api_router.*`：新增社区 API 路由与 JSON 响应。
- `http/http_conn.*`：传递登录用户信息、CSRF 和请求上下文。
- `root/community.html`：改为动态 Feed 页面。
- `README.md` / `docs/`：补充迁移和接口说明。

验收标准：分页无重复/漏项，未登录访问与非法写请求被正确拒绝，行为可以准确写入数据库。

### 阶段 2：统一内容元数据与社区索引（2～3 天）

修改内容：

- 扩展 `DocumentChunk`，加入内容类型、来源 ID、作者、时间和状态元数据。
- 将 `KnowledgeIndexer` 的公共逻辑抽取为可服务知识文档和社区帖子的内容索引能力。
- 给 `VectorStore`、HNSW 和 BM25 增加来源过滤能力。
- 发布帖子后建立或排队建立帖子 Embedding。
- 支持帖子新增、更新和逻辑删除后的索引同步。
- 知识索引和社区索引物理隔离或使用严格元数据过滤。

验收标准：同一检索内核可以只搜知识、只搜社区或同时搜索；删除/屏蔽帖子不会继续被推荐。

### 阶段 3：兴趣画像与推荐排序（2～3 天）

修改内容：

- 根据用户近期和长期行为计算兴趣向量。
- 实现多路召回：兴趣相似、热门、最新和探索内容。
- 实现融合排序：语义相似度、互动质量、时间衰减和负反馈。
- 加入已看降权、作者去重、内容去重和随机探索。
- 新用户回退到高质量热门内容，并逐步学习兴趣。

第一版参考权重：

```text
推荐分 = 语义相似度 × 0.45
       + 互动质量   × 0.20
       + 内容质量   × 0.15
       + 新鲜度     × 0.10
       + 探索分     × 0.10
```

权重通过配置管理，不写死为不可调整的业务常量。

验收标准：不同兴趣账号得到不同排序；不感兴趣能明显降权；无画像或 AI 异常时仍能返回稳定结果。

### 阶段 4：RAG 与社区双向融合（2～3 天）

修改内容：

- RAG 检索上下文增加 `source_type` 筛选和社区内容开关。
- RAG 回答返回相关社区帖子列表，并明确标注“社区经验”。
- 社区帖子增加相关知识、相关帖子和“基于此内容提问”入口。
- 将用户问题向量作为短期兴趣信号，但设置衰减，避免一次提问长期改变推荐。
- Prompt 中区分知识库资料和社区内容的可信度。

验收标准：RAG 引用来源类型清晰；关闭社区检索时行为与原系统一致；帖子页可以自然进入问答流程。

### 阶段 5：测试、性能与交付（2～3 天）

修改内容：

- 增加 Feed API、行为写入、过滤、排序、冷启动和故障回退测试。
- 增加统一索引持久化兼容性和升级测试。
- 验证并发 Feed 请求不会阻塞登录、上传或 SSE 问答。
- 增加推荐耗时、候选数、Embedding 失败和回退指标。
- 更新 README、配置示例、数据库迁移、部署和回滚说明。

验收标准：全部自动化测试通过；旧索引不兼容时能明确检测并安全重建；推荐服务故障不影响社区基本浏览。

## 6. 建议的代码结构

在保留现有目录的前提下逐步演进，避免一次性大规模重构：

```text
ai_rag/
├── embedding_provider.*       # 继续复用
├── vector_store.*             # 增加内容元数据与过滤
├── hnsw_index.*               # 增加来源过滤/映射
├── hybrid_retriever.*         # 场景化检索
├── content_indexer.*          # 新增统一内容索引
└── rag_service.*              # 保留生成答案职责

community/
├── community_repository.*     # 帖子与行为数据库访问
├── user_profile.*             # 用户兴趣画像
└── recommendation_service.*   # 召回、融合、排序、回退

api/
└── api_router.*               # Feed 与行为接口

root/
└── community.html             # 动态社区页面
```

## 7. 数据库改动原则

- 保留 `user_posts` 作为社区业务主表，不直接迁移或删除现有帖子。
- 新增行为表、AI 内容状态表和必要索引。
- 所有迁移使用 `CREATE TABLE IF NOT EXISTS` 或明确的版本记录，避免重复执行造成破坏。
- 向量优先保存在现有文件索引中，MySQL 保存来源映射、处理状态和行为数据。
- 帖子采用逻辑删除/屏蔽，索引同步后再清理物理数据。

建议新增的逻辑表：

```text
community_actions       用户行为事件
community_post_stats    帖子聚合统计
ai_content_registry     统一内容来源、类型和索引状态
user_interest_profiles  用户兴趣画像版本与更新时间
schema_migrations       数据库迁移版本
```

## 8. API 规划

```text
GET  /api/community/feed
POST /api/community/action
GET  /api/community/posts/:id/related
POST /api/ask                         # 保留，扩展来源类型
```

Feed 响应除帖子数据外，还应包含不透明游标和推荐追踪 ID：

```json
{
  "items": [],
  "next_cursor": "opaque-cursor",
  "request_id": "recommendation-request-id",
  "fallback": false
}
```

行为事件携带推荐追踪 ID，便于判断一次曝光来自哪个推荐结果；服务端不信任前端提交的用户名。

## 9. 测试范围

- 单元测试：兴趣向量、时间衰减、分数融合、过滤、去重和游标编码。
- API 测试：登录、CSRF、参数边界、分页、幂等和限流。
- 索引测试：来源过滤、增量加入、删除同步、保存加载和版本兼容。
- 集成测试：发布帖子后可索引、推荐后可记录行为、帖子可进入 RAG 问答。
- 容错测试：Embedding、Rerank、MySQL 或索引不可用时安全回退。
- 回归测试：现有 RAG、SSE、登录、上传和静态资源功能继续正常工作。

## 10. 不在首版范围内

- 基于深度神经网络的 CTR/停留时间预测模型。
- 视频语音识别、逐帧理解和实时转码。
- 完整评论系统、关注关系和私信系统。
- 大规模分布式向量数据库与消息队列集群。
- 自动内容审核的最终裁决；AI 只能作为风险提示，不能替代安全策略。

这些能力应在获得足够真实行为数据和明确业务需求后再实施。

## 11. 阶段性交付与回滚

每个阶段独立提交并附带测试，不把全部改动压在一个不可拆分的提交中：

1. 数据库与动态 Feed。
2. 行为采集。
3. 统一内容索引。
4. 兴趣画像与推荐排序。
5. RAG/社区融合入口。
6. 性能、指标和文档。

动态 Feed、个性化推荐和社区参与 RAG 均使用独立配置开关。出现故障时可以依次回退为：

```text
AI 个性化推荐 -> 规则热门推荐 -> 按时间倒序
社区增强 RAG   -> 仅知识库 RAG
```

## 12. 最终验收定义

满足以下条件视为完整融合版完成：

- 社区使用动态分页 API，不再依赖发布后重建完整页面。
- 用户行为被安全采集并用于兴趣画像。
- 推荐结果同时考虑语义兴趣、热度、新鲜度、负反馈和探索。
- 知识文档与社区帖子共用检索基础能力，但可以严格过滤和独立维护。
- RAG 页面能展示相关社区讨论，帖子页面能进入相关知识和 AI 问答。
- AI 或推荐组件异常时可回退，原有登录、上传和 RAG 问答不受影响。
- 新增功能具有自动化测试、指标、配置说明、数据库迁移和回滚文档。
